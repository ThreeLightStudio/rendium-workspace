# ADR 004: Studio Product Domain Boundary (Studio 제품 도메인 경계)

[English](../en/004-studio-product-domain-boundary.md)

- **상태**: 제안됨
- **날짜**: 2026-05-12
- **맥락**: `desktop-studio`는 ProductCommand, Product Context, Headless Workflow 개념들을 별도의 워크스페이스 패키지로 분리할지 결정하기 전에, 더 명확한 내부 경계를 설정할 필요가 있습니다.

## 맥락

ADR 001은 엔진 인텐트 위에 Studio 소유의 액션으로 ProductCommand를 정의했습니다. ADR 002는 AI 및 UI가 사용하는 읽기 측 제품 의미로서 Product Context를 정의했습니다. ADR 003은 ProductCommand 위의 결정론적 레시피로서 Headless Workflow를 정의했습니다.

다음 워크플로우 요구사항은 JSON 준비 상태의 위저드 규약(wizard contract)입니다:
- 워크플로우 프리셋이 데이터로 표현되어야 합니다.
- 위저드 단계(wizard steps)가 워크플로우 정의로부터 제공되어야 합니다.
- 각 단계는 필수(required) 또는 선택(optional) 여부를 선언해야 합니다.
- 선택적 단계는 건너뛸(skippable) 수 있어야 합니다.
- 필수 단계는 UI 내비게이션과 컴파일 검증을 모두 구동해야 합니다.
- 컴파일러가 필요로 하는 워크플로우 정책을 UI가 중복해서 구현하지 않아야 합니다.

이로 인해 UI, ProductCommand, Product Context 및 워크플로우 정의 간의 경계가 더욱 중요해졌습니다.

향후 매력적인 방향이 있습니다: Studio 제품 정책을 `@rendium/studio-product`와 같은 전용 워크스페이스 패키지로 이동하는 것입니다. 이 패키지는 제품 명령, 컨텍스트 팩, 워크플로우 카탈로그 로딩, 프리셋 검증 및 결정론적 컴파일을 소유할 수 있습니다.

그러나 현재 구현은 여전히 `desktop-studio` 렌더러 영역과 긴밀하게 연결되어 있습니다:
- ProductCommand가 선택 동작을 위해 렌더러 스토어를 호출할 수 있습니다.
- 일부 실행 헬퍼가 로컬 타임라인 재생 컨트롤러를 탐색합니다.
- Product Context가 Studio 소유의 프로젝트 에셋 레코드를 사용합니다.
- AI 컨텍스트 타입이 현재 데스크톱 앱 공유 레이어에 존재합니다.
- 워크플로우 컴파일이 ProductCommand 리졸버 동작 및 Studio 에셋 시맨틱에 의존합니다.
- Storybook이 사용자 대면 워크플로우의 주요 리뷰 영역으로 남아 있습니다.

지금 워크스페이스 패키지를 추가하면 도메인 경계가 안정되기 전에 또 다른 온보딩 단계를 만들게 됩니다. 새로운 기여자는 API가 여전히 변경되는 동안 앱 패키지와 새로운 패키지 경계를 모두 이해해야 합니다.

## 결정 사항

v1에서는 `desktop-studio` 내부의 **Internal First (내부 우선)** 제품 도메인 경계를 적용합니다.

의미하는 바:
- 아직 `@rendium/studio-product`를 생성하지 않습니다.
- ProductCommand, Product Context, Headless Workflow의 소유권을 `desktop-studio`로 유지합니다.
- 패키지를 추출하기 전에 내부 제품 도메인 형태로 먼저 구조화해 나갑니다.
- 실용적인 범위 내에서 렌더러 사이드 이펙트를 제품 도메인 코어 외부에 둡니다.
- 워크플로우 정의가 필수/선택적 위저드 단계 및 컴파일 검증의 단일 진실 공급원이 되도록 합니다.

선호되는 내부 네임스페이스는 다음과 같습니다:
```text
src/renderer/src/productDomain/
  commands/
  context/
  workflows/
  types/
```

이 이름은 의도적으로 서술적입니다. 이 코드가 여전히 데스크톱 앱 내부에 존재하면서도 React 컴포넌트, Storybook 스토리, Zustand 스토어, Electron 브릿지 및 시각적 UI 관심사로부터 분리되어 있음을 나타냅니다.

기존의 `productCommands`, `productContext` 및 `workflows` 폴더는 이 형태로 점진적으로 마이그레이션될 수 있습니다. 마이그레이션이 단일 이름 변경으로 일어날 필요는 없으며, 동작을 유지하는 리팩토링은 워크플로우 구동 UI 변경이 해당 경계를 필요로 할 때만 수행되어야 합니다.

## 규칙

- 제품 도메인 코드는 manifest, snapshot, intent 타입을 포함하여 공개 `@rendium/engine` 규약에 의존할 수 있습니다.
- 제품 도메인 코드는 데이터, 인텐트, 요약 또는 에러를 반환하는 순수 리졸버 함수를 선호해야 합니다.
- 제품 도메인 코드는 React 컴포넌트를 임포트해서는 안 됩니다.
- 제품 도메인 코드는 Storybook 유틸리티를 임포트해서는 안 됩니다.
- 제품 도메인 코드는 Electron API를 직접 호출해서는 안 됩니다.
- 제품 도메인 컴파일 함수는 엔진 상태를 직접 변경해서는 안 됩니다.
- 렌더러 사이드 이펙트는 앱 어댑터, 컴포넌트, 훅 또는 스토어에 유지합니다.

렌더러 사이드 이펙트의 예시:
- `engineStore.executeAtomicIntentBatch()`
- `useStudioStore`에서의 레이어 선택
- 타임라인 재생 컨트롤러 호출
- 파일 입력, 업로드 및 프로젝트 에셋 영속성
- 토스트 알림
- 모달 열기/닫기 상태

이러한 사이드 이펙트들은 제품 도메인 결과를 래핑할 수는 있으나, 해당 결과를 계산하는 데 필수적으로 요구되어서는 안 됩니다.

## 워크플로우 정의 방향

워크플로우 정의는 도메인 로직과 UI 사이의 교량 역할을 해야 합니다.

워크플로우 정의는 다음을 기술해야 합니다:
- 사용 가능한 프리셋
- 에셋 슬롯
- 순서가 지정된 단계
- 각 단계의 필수 또는 선택 여부
- 선택적 단계를 건너뛸 수 있는지 여부
- 기본 파라미터
- 컴파일 동작

위저드는 `0 | 1 | 2 | 3 | 4`와 같은 하드코딩된 숫자 단계 대신 이 정의로부터 렌더링되어야 합니다.

컴파일러는 단계 메타데이터를 단순히 디스플레이 전용 정보로 취급하는 대신 동일한 정의를 기반으로 유효성을 검증해야 합니다.

오디오 비주얼 초안 워크플로우의 경우, `requiredAssetSlots`가 수동적인 프리셋 메타데이터에 머무르지 않고 `WorkflowWizard`와 `compileSelectedWorkflow` 양쪽에서 사용하는 더 풍부한 워크플로우 규약의 일부가 되어야 함을 의미합니다.

## 향후 패키지 추출 기준

내부 제품 도메인 경계가 다음 기준을 만족한 후에만 전용 워크스페이스 패키지 적용을 다시 검토합니다:

- 제품 도메인 코어가 React, Zustand, Electron, Storybook을 임포트하지 않고 타입 검사를 통과함.
- 데스크톱 렌더러를 마운트하지 않고도 제품 도메인 테스트가 정상 실행됨.
- 워크플로우 카탈로그 데이터가 UI 내비게이션과 컴파일 검증 모두에서 사용됨.
- ProductCommand 리졸버가 렌더러 사이드 이펙트를 실행하지 않고 결정론적인 출력을 생성할 수 있음.
- AI 컨텍스트 생성기가 렌더러 스토어를 임포트하지 않고 제품 도메인 타입을 소비할 수 있음.
- 새로운 기여자가 `desktop-studio` UI 구현 전체를 먼저 읽지 않고도 제품 도메인의 공개 API를 이해할 수 있음.

이 기준들이 유지된다면 `@rendium/studio-product`와 같은 패키지로의 추출을 재검토할 수 있습니다.

## 결과 및 영향

- 새로운 워크스페이스 패키지가 도입되지 않으므로 현재로서는 온보딩이 더 간단하게 유지됩니다.
- 도메인 경계가 공개 패키지 API가 되기 전에 `desktop-studio` 내부에서 먼저 안정화될 수 있습니다.
- 워크플로우 정책이 테스트 가능한 도메인 모듈로 이동하는 동안 Storybook은 UI 근처에 그대로 유지됩니다.
- 에셋 레코드, AI 컨텍스트, 선택 동작 및 타임라인 탐색을 중심으로 일부 단기적인 결합이 남아 있습니다.
- 내부 경계를 통해 순수해야 하는 영역과 앱 어댑터로 남아야 하는 영역이 명시되므로 향후 추출이 더 용이해집니다.

## 후속 작업

- `WorkflowWizard`를 숫자 단계에서 워크플로우 정의 단계로 리팩토링합니다.
- 필수/선택적 워크플로우 단계 메타데이터를 위저드 내비게이션의 단일 진실 공급원으로 승격시킵니다.
- 동일한 필수/선택적 메타데이터를 컴파일 검증에 사용합니다.
- 제품 도메인 컴파일이 성공한 후에는 렌더러 사이드 이펙트를 로컬 어댑터에 유지합니다.
- 내부 경계에 대한 테스트와 안정적인 임포트가 마련된 후에만 패키지 추출을 재평가합니다.
